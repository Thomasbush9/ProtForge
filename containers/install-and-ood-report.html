1. Current state — what's actually there

ProtForge runs a 4-stage GPU pipeline (MSA → Boltz → ESM/ESMFold → ES) orchestrated by Snakemake, with a Streamlit webapp as the front-end. The design splits cleanly into two layers:

Host (orchestrator)

Small Python venv from requirements-host.txt. Runs Snakemake + the SLURM executor plugin + the Streamlit webapp. Calls sbatch/squeue/sacct natively. Not containerized — by design.

Compute (per stage)

Each SLURM job runs singularity exec --nv … <sif> python <stage_script>. Big databases and model weights are bind-mounted at runtime, never baked into the image.

The "orchestrator on host, compute in container" split is deliberate and correct — binding the Munge socket / libslurm / /etc/slurm into a container to run sbatch is the brittle path everyone avoids (GATK / Nextflow / Snakemake-on-HPC all do orchestrator-on-host). Keep this. The install pain is entirely on the compute-container + weights side.

What gets bind-mounted (not in any image)

AssetSizeMount point
ColabFold MSA databases~700 GB/data/colabfold_db
Boltz checkpoint~5 GB/data/boltz_db
ESM-C / ESMFold HF cache~10 GB/models/hf

These are shared on Kempner already, so users never download the 700 GB. Good. This is why the images themselves are "just tooling" and stay relatively small.

The user-facing symptom of all this: a new lab member follows CLUSTER_SETUP.md, runs build.sh, and hits a missing-file error on line one. That is the install difficulty. It isn't fundamentally a containers problem — it's a "the repo can't decide which design it's on" problem.

3. Keep per-stage — make the many-container install easy

Per-stage stays. The goal isn't fewer images; it's that installing N images feels like installing one. Each independent def file (msa.def, boltz.def, esmfold_cu.def, openfold.def, + a future es.def) lets you bump Boltz, swap an ESM size, or update OpenFold3 and rebuild/revalidate only that image — no cross-tool constraint solving, no risk to the other stages. That's worth the disk and the extra files. Below is how to remove the friction without touching that property.

1A build_all.sh that loops the def files

One driver over the existing build.sh machinery (cache/tmp handling, fakeroot, logging are already solid there). It iterates a manifest of (stage → def → output sif), builds or pulls each, and skips ones already present. Adding a model later = drop in one def + one manifest line. Modularity preserved, single command.

# manifest: stage  def              sif
msa       msa.def         protforge-msa.sif
boltz     boltz.def       protforge-boltz.sif
esmc      esmfold_cu.def  protforge-esmc.sif
openfold  openfold.def    protforge-openfold.sif

bash containers/build_all.sh                 # build all missing
bash containers/build_all.sh boltz           # rebuild just one  ← the modularity payoff
bash containers/build_all.sh --from-docker   # pull all from GHCR

2Publish per-image to GHCR highest leverage

The single biggest friction reducer, and it fits per-stage perfectly: a CI matrix builds one image per def on change and pushes ghcr.io/<org>/protforge-<stage>:<tag>. Users then pull instead of running a ~30-min --fakeroot build (which may not even be permitted on their partition). Because images are independent, CI only rebuilds the stage whose def changed — modular builds end-to-end. Tag per-image (e.g. protforge-boltz:2.2.1) so a model bump is a visible, revertable version.

3Optional: shared base layer to kill the duplication

The honest cost of per-stage is repeated torch+CUDA (~3-5 GB each, ×4). If that matters, build one protforge-base.sif (ubuntu + torch + CUDA runtime) and have the stage defs Bootstrap: localimage from it. Tradeoff to weigh against your modularity goal: a base rebuild forces all children to rebuild, and it re-couples the torch/CUDA version across stages — which is partly what you went per-stage to escape (note boltz.def and esmfold_cu.def currently sit on different torch/CUDA: cu128 + torch 2.9.1 vs slim+cu128). recommend: skip unless disk is actually a problem — full independence is cheap in dollars and is the thing you actually want.

4Fix the config schema to match per-stage already close

config.template.yaml already has the right shape — five per-stage fields (colabfold/boltz/esmc/esmfold/openfold) each pointing at its own SIF. This is correct for your design; the "collapse to one field (audit H4)" note in the docs was written for the abandoned single-SIF world and should be dropped, not acted on. Just make the docs stop apologizing for having five fields.

4. One install.sh — proposal

The building blocks already exist; they're just not behind one door:

PieceTodayRole in install.sh
Config generation + conda pathsetup.sh (on containers branch)Prompt for account/email/paths, emit config.yaml
Image build/pullcontainers/build.shBuild or --from-docker pull the SIF(s)
Weights downloadscripts/download_models.pyPopulate $PROTFORGE_ROOT/models/hf
Host envrequirements-host.txtpython -m venv + pip for Snakemake/webapp
Validationcontainers/test/smoke.shFinal "it works" check

A single install.sh at repo root that runs these in order, with sane defaults and a --mode kempner|custom flag (Kempner mode skips downloads since DBs/weights/envs are shared):

bash install.sh --mode kempner --account kempner_xxx_lab --email you@x.edu
#  1. resolve $PROTFORGE_ROOT layout, create sifs/ models/ caches
#  2. host venv  <- requirements-host.txt
#  3. fetch image(s):  build.sh --from-docker ...   (fallback: --from-def)
#  4. weights:    download_models.py   (skipped in kempner mode)
#  5. render config.yaml from template + answers
#  6. smoke.sh
#  -> prints: "Edit config.yaml SLURM section, then: streamlit run webapp/app.py"

This is mostly assembly of code you already wrote, plus restoring setup.sh's logic. The hard 80% (image build, weights, config schema) is done. low risk

Decision needed: do you keep two install paths (container + conda), or commit to containers as the only supported path and let conda bit-rot? Maintaining both doubles the test surface. Given the webapp + Snakemake are host-side anyway, I'd make container the only documented path and keep conda as an undocumented escape hatch.

5. Open OnDemand integration

docs/WEBAPP.md already lays out the three access options (SSH -L, VS Code Remote-SSH, Open OnDemand) and correctly recommends OOD for tunnel-free / shared / compute-node use. What's missing is the actual OOD app — the docs describe it as a thing to "ask FASRC for," but nothing is built.

What an OOD interactive app is

A small directory of files in your OOD sandbox that renders a web form, then submits a SLURM job running your app on a compute node, and proxies its port back through the OOD portal as a one-click link. For ProtForge it's ~5 files:

FilePurpose
manifest.ymlName, category, icon — what shows in the OOD "Interactive Apps" menu
form.ymlThe form: partition, account, GPUs?, walltime, session dir. (Mostly host-side, so a CPU node is fine.)
submit.yml.erbMaps the form to SLURM directives (--account, --partition, time, mem)
template/script.sh.erbActivates the host venv and runs streamlit run webapp/app.py --server.port ${port} --server.address 0.0.0.0 --server.headless true
template/before.sh.erb + view.html.erbPicks a free ${port}, then OOD proxies it and renders the "Connect to ProtForge" button

How it fits ProtForge specifically

  • The webapp is already a launcher (it shells out to sbatch and owns the Snakemake controller), so running it on an OOD-allocated compute node is strictly better than a login node — it survives the controller's full lifetime and respects login-node etiquette. The webapp's tmux advice in WEBAPP.md becomes unnecessary: OOD keeps the session alive.
  • The OOD job needs the host venv only (Snakemake + Streamlit). It does not need a GPU — the GPU work is in the SIFs that Snakemake submits as separate jobs. So the OOD form should default to a small CPU allocation. cheap session
  • Streamlit must bind 0.0.0.0 (not 127.0.0.1 as in the current docs) and set --server.baseUrlPath/enableCORS=false so it works behind OOD's node proxy. Minor flag changes from the documented invocation.
  • Sessions already live in .sessions/<id>/, so multiple OOD launches won't collide on config.

Two tiers of effort

  1. Zero-build (today): launch an OOD Remote Desktop or Jupyter session, open a terminal, run the documented streamlit command, browse localhost:${port} inside it. Works now, no FASRC ask. Document this as the interim path.
  2. Custom app (the real deliverable, ~1 day): the 5-file app above → a one-click "ProtForge" button for you and labmates, no tunnel, on a compute node. Requires the FASRC interactive-app sandbox path (e.g. ~/ondemand/dev/protforge) — this is the one external dependency: ask Kempner/FASRC support for sandbox enablement.

Keep the existing guidance to avoid public tunnels (ngrok/cloudflared) — they expose an unauthenticated Streamlit app to the internet and violate cluster AUP. OOD is the sanctioned answer.

7. Recommended next steps

  1. De-drift to per-stage. Point build.sh at the per-stage defs (or wrap them in build_all.sh), and rewrite CLUSTER_SETUP.md / README.md / CONTAINERS.md to describe the many-container design as the intended one. Delete the single-SIF references and the "collapse to one field" (H4) note. This unblocks everything and is pure cleanup — no design decision left to make.
  2. Add build_all.sh + one top-level install.sh wrapping per-stage build/pull + download_models.py + host venv + smoke test, emitting a ready-to-edit config.yaml. Low risk — assembly of existing pieces.
  3. Publish per-image to GHCR with a CI matrix (one job per def, rebuild only the changed stage) so users pull instead of build --fakeroot. Highest leverage per hour, and it keeps builds modular.
  4. Build the OOD interactive app (~5 files, ~1 day) once the host-venv install is stable. Ask FASRC for the sandbox path in parallel — the only external dependency. Document the zero-build Remote-Desktop fallback as interim.
  5. Finish per-stage E2E validation (TESTING.md Step 2) and make container the single documented install path; demote conda to an escape hatch.

Sequencing: 1 → 2/3 (parallel) → 4 → 5. Step 1 is now pure cleanup (no decision pending) since the per-stage design is settled. The OOD work (4) is independent of the container shape and can start as soon as the host venv install is reliable.

Generated for decision-making, not as a spec. Per-stage containers are the settled design; the prerequisite is just making the repo (docs + build.sh) agree with that. "Easier install" and "Open OnDemand" are both straightforward from there.
