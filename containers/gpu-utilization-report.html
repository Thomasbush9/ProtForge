ProtForge — GPU Utilization Review & Optimization Plan

Where the GPUs idle today, and the concrete changes that close the gap — written from an NVIDIA performance-engineering lens.

Scope: the GPU stages (ESM-C, ESMFold2, ESM-C/SAE, Boltz, OpenFold3) and their SLURM dispatch. Job-level parallelism (dependency graph, chunking, array fan-out) is already solid; this targets per-GPU efficiency.

TL;DR

The pipeline is well-decomposed at the job level but leaves large amounts of device-level throughput on the table. The dominant losses, in priority order:

  1. No mixed precision / TF32. Every model loads in fp32 and runs without autocast. On H100 this forfeits the tensor-core path — typically 1.5–3× for free with bf16/TF32.
  2. ESMFold2 and SAE run batch=1 in a Python for loop. The GPU drains between sequences. Real batching (with length bucketing) is the single biggest fold/SAE win.
  3. ESM-C pads the whole chunk to the longest sequence. One 800-aa outlier inflates a 25× batch of 150-aa peptides to 800 columns — most FLOPs are spent on padding.
  4. One job → one whole GPU. 300M/600M ESM-C and ESMFold underfill an H100 (often <30% SM occupancy) yet hold the full card. No MPS/MIG sharing.
  5. Cold weight load per chunk. Each SLURM job reloads weights from shared storage + HtoD copy; for ESM-C-6B that is minutes of GPU idle amortized over only 25 sequences.

Most fixes are localized to the four runner scripts and the SLURM resource block — no architectural change to the Snakemake graph.

1 · How I assessed it

I read the GPU dispatch path end to end: the SLURM resource blocks and singularity exec --nv invocations in workflow/rules/{esmc,esmfold,boltz,openfold}.smk, the slurm_extra() GPU-request helper in Snakefile, and the actual device work in containers/run_batch_esmc.py, run_batch_esmfold.py, and esmc_extract_sae.py.

The lens is standard NVIDIA inference triage: are tensor cores active (precision)? · is the SM array fed (batch/occupancy)? · is the device shared when one model can't fill it (MPS/MIG)? · are we paying kernel-launch / cold-load overhead we could amortize (graphs, persistent workers)?

3 · Tier 1 — free wins (precision + load)

These are low-risk, touch only the runners, and apply to every in-house stage. Do these first.

1.1 Turn on TF32 + bf16 autocast

Add a one-time preamble in each runner's __main__ before any forward. On H100/A100 this routes matmuls through tensor cores at near-zero accuracy cost for inference embeddings/structure.

import torch
torch.backends.cuda.matmul.allow_tf32 = True
torch.backends.cudnn.allow_tf32 = True
torch.backends.cuda.matmul.fp32_precision = "tf32"  # newer torch alias

# wrap the forward:
with torch.inference_mode(), torch.autocast("cuda", dtype=torch.bfloat16):
    outputs = model(**inputs)

Applies to run_batch_esmc.py:encode_sequences / encode_for_logits, run_batch_esmfold.py (wrap builder.fold(...)), and esmc_extract_sae.py:forward_sae. For ESMFold/structure, bf16 is safer than fp16 (no loss-scaling, wide dynamic range). Validate pLDDT/pTM parity on the smoke fixture — see §7.

Note: logits in encode_for_logits already cast back to fp32 on CPU (outputs.logits.float().cpu()), so LLR math downstream is unaffected by an autocast forward.

1.2 Stop reloading weights cold for every chunk

Each chunk is its own SLURM job that runs from_pretrained(...).cuda() from scratch. For ESM-C-6B that is a multi-GB read off shared LFS + HtoD copy, amortized over only max_files_per_job=25 sequences. Two levers:

  • Raise max_files_per_job for the small/cheap models so the fixed load cost is spread over more work. The bin-aware chunker already exists (binning: in config) — extend the recipe so short-sequence bins pack many more per chunk.
  • Persistent in-job server for many-chunk runs: when one job folds a large input dir, keep the model resident and stream sequences — which is exactly what the batching change in §4 enables. The model is loaded once per job already; the gain is making each job do more forwards before exit.
Rule of thumb: if model-load time is a double-digit % of job wall-time (check the BENCH_INFER_S lines vs total job time in benchmarks/<stage>/*.tsv), the chunk is too small for that model.

4 · Tier 2 — batching & padding

2.1 ESMFold2 & SAE: replace the per-sequence loop with real batches

Today:

# run_batch_esmfold.py
for name, sequence in seq_by_name.items():
    result = builder.fold(model, spi, ...)   # one sequence, GPU drains after

ESMFold2 supports multi-chain / multi-sequence input building; SAE is a plain transformer forward that already tokenizes with padding=True — it just never receives more than one sequence. Change both to:

  1. Length-sort the chunk's sequences.
  2. Pack into micro-batches by a token budget (e.g. sum(len) ≤ B), not a fixed count — keeps padding tight and memory bounded.
  3. Forward each micro-batch once under autocast; slice per-sequence outputs back out (the SAE saver already trims to seq_len, so the per-row logic is mostly there).

This is the highest-value change for the two starved stages: it converts a string of tiny kernels into a few large ones, raising SM occupancy and cutting per-sequence launch overhead.

2.2 ESM-C: length-bucketed batching instead of one chunk-wide pad

The single tokenizer(sequences, padding=True) pads to the chunk maximum. With mixed lengths the wasted-FLOP fraction is roughly 1 − mean(len)/max(len) — easily 50%+ on heterogeneous chunks. Fix:

order = sorted(range(len(sequences)), key=lambda i: len(sequences[i]))
for batch_idx in token_budget_batches(order, sequences, budget=TOKENS):
    enc = tokenizer([sequences[i] for i in batch_idx], padding=True, return_tensors="pt")
    with torch.inference_mode(), torch.autocast("cuda", torch.bfloat16):
        out = model(**enc.to(model.device))
    # map rows back to original names via batch_idx

Same primitive as 2.1 — implement token_budget_batches once in a shared helper and reuse across all three runners.

2.3 Pin host memory + non-blocking copies

Tokenized tensors move HtoD with default (pageable) memory. For the batched path, pin_memory() + .to(device, non_blocking=True) overlaps copy with compute. Marginal next to 2.1/2.2 but free once batching exists.

5 · Tier 3 — device sharing (MPS / MIG)

Even after batching, a 300M/600M ESM-C or a single short-protein ESMFold rarely fills an H100. The pipeline currently requests one whole GPU per job (slurm_extra(gpu=...) emits --gpus-per-node=1, runners hardcode CUDA_VISIBLE_DEVICES=0). Two NVIDIA mechanisms reclaim the idle SMs:

CUDA MPS recommended first

Multi-Process Service lets several processes share one GPU context with real concurrent kernel execution. Co-locate N small jobs on one card.

  • Start nvidia-cuda-mps-control -d in the job prologue (or a wrapper).
  • Pack multiple chunks per GPU via SLURM --gpus-per-task sharing or by launching several runner processes in one job.
  • Best for the embedding/SAE stages where each process is light and memory fits several-fold.

Gate behind a config flag (esmc.mps: true) — not all partitions allow it.

MIG (A100/H100) partition-dependent

Hard-partition one physical GPU into isolated slices (e.g. 7× on A100). Each slice is a fully isolated mini-GPU with guaranteed memory.

  • Cleaner isolation than MPS, better for guaranteed-memory small models.
  • Requires admin-configured MIG profiles on the partition; request a slice via --gres=gpu:1g.10gb:1-style specs.
  • Coordinate with Kempner ops — this is a cluster-config dependency, not a code change.

The code-side enabler for both: stop hardcoding CUDA_VISIBLE_DEVICES=0 in the rule shells and let SLURM/MPS assign the device, plus a small dispatch flag to fold several chunks into one GPU allocation for the cheap stages.

6 · Tier 4 — graph/compile & advanced

  • torch.compile on the resident model. ESMFold2's diffusion/recycling loops re-run identical-shape forwards; model = torch.compile(model) (or the structure module) cuts kernel-dispatch overhead and fuses ops. Pays off only when the model is reused across many sequences — i.e. after §4 batching lands. Bucket shapes to limit recompiles.
  • CUDA graphs for the diffusion sampler. num_sampling_steps=50 repeats the same kernel sequence; capturing it as a CUDA graph removes per-step launch latency. Higher effort; revisit if profiling shows launch-bound steps.
  • Boltz flags, not Boltz code. Boltz already exposes --no_kernels/subsample_msa/use_potentials through boltz.advanced. Profile whether the custom Triton kernels (default on) beat the fallback on the target GPU; tune diffusion_samples/recycling_steps for the throughput/quality point you actually need (25/10 is generous).
  • OpenFold3 is already the model citizen — Lightning batching across up to 4 GPUs. Leave the dispatch alone; only revisit num_workers if the dataloader is the bottleneck (check GPU util during its jobs).

7 · How to measure the wins

Don't trust the changes — measure them. The harness already emits BENCH_INFER_S per forward and Snakemake benchmark: TSVs per job.

  • Before/after on the smoke fixture (containers/test/smoke.fasta + the test scripts): assert structure metrics (pLDDT/pTM) and embedding/logit values match within tolerance — precision & batching must not move results beyond fp tolerance.
  • Device occupancy: run one job under nvidia-smi dmon -s u or nsys profile; SM% before vs after batching is the headline number.
  • Throughput: sequences/GPU-hour from the benchmarks/*.tsv wall-times. This is the metric that maps to cluster cost.
  • Load fraction: compare summed BENCH_INFER_S against job wall-time to quantify the cold-load tax §1.2 targets.

9 · Risks & non-goals

  • Numerical parity is the gate. bf16/batched paths must reproduce the fp32/serial results within tolerance on the smoke fixtures before rollout. The SAE and logit savers already pin output dtype (fp16/fp32 on CPU), so storage format is unchanged — only the compute path moves.
  • OOM from over-batching. Token-budget batching (not fixed count) bounds peak memory; tune the budget per model size, reusing the existing per-size SLURM mem_mb overrides.
  • MPS/MIG are partition-dependent. Keep them behind config flags; the default path stays one-GPU-per-job so nothing breaks on partitions without them.
  • Non-goals: the job graph, chunking dependency logic, and MSA stage are out of scope — they're already efficient and not GPU-bound in the same way. OpenFold3's dispatch is left as-is.
