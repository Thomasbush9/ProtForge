ProtForge → Personal GPU

Review of the current SLURM-coupled, container-based pipeline and a concrete plan to make it run on a personal NVIDIA GPU machine.

Branch singularity · scope: containers/ + Snakemake orchestration + webapp · generated 2026-06-15

TL;DR — the verdict

Good news: the hard part is already done. Every GPU stage already runs inside a container via singularity exec --nv … <image>, and those shell commands are executor-agnostic — they do not care whether Snakemake submits them through SLURM or runs them as plain local processes. You are roughly 80% of the way to a personal-GPU build.

What actually ties the pipeline to a cluster is a thin, well-localized layer: (1) the only Snakemake profile is profiles/slurm/; (2) every GPU rule hardcodes CUDA_VISIBLE_DEVICES=0, which is correct only because SLURM hands each job an isolated single-GPU cgroup; (3) the webapp hardcodes --profile profiles/slurm/; and (4) the data model assumes cluster-shared storage for a ~700 GB MSA database.

None of these are deep. The two items that take real thought are multi-GPU scheduling (SLURM was doing your GPU allocation for free) and the 700 GB MSA DB (the answer for personal machines is to use the remote ColabFold MSA server instead of hosting it).

1 · How the pipeline works today

ProtForge is a Snakemake workflow that chains protein-prediction stages: MSA (ColabFold/MMseqs2) → Boltz (structure), with ESM-C (embeddings), ESMFold2, and OpenFold3 running in parallel off the same inputs. Each GPU stage is a .smk rule whose shell block wraps the stage's tool in a container call. A representative example (ESM-C, workflow/rules/esmc.smk:160):

{params.runtime} exec --nv --cleanenv \
    --env HF_HOME=/models/hf  --env HF_HUB_OFFLINE=1 \
    -B {params.cache_dir}:/models/hf:ro \
    -B {input.chunk_dir}:{input.chunk_dir}:ro \
    -B {params.output_dir}:{params.output_dir} \
    {params.sif} \
    python /opt/run_batch_esmc.py --cache /models/hf --size {wildcards.size} …

The image path comes from config (containers.esmc, or the shared containers.gpu fallback) via container_sif() in the Snakefile:160. Model weights and databases are never baked into the image — they are bind-mounted at runtime. Job submission goes through the SLURM executor profile (profiles/slurm/config.yaml), and the webapp shells out to snakemake --profile profiles/slurm/.

3 · What couples it to SLURM

Four things, each narrow:

3.1 · Only a SLURM execution profile exists core change

profiles/slurm/config.yaml:6 sets executor: slurm and jobs: 100. There is no profiles/local/ — the README explicitly lists it under "Not yet covered (deferred)." The good news: the per-rule slurm_partition / slurm_account / slurm_extra resource fields are silently ignored by Snakemake's local executor, so adding a local profile needs almost no rule edits.

3.2 · Every GPU rule hardcodes CUDA_VISIBLE_DEVICES=0 multi-GPU blocker

Present in msa.smk:95, boltz.smk:160, esmc.smk:141, esmc_sae.smk:126, esmfold.smk:126. Under SLURM this is correct: each job runs in a cgroup that exposes exactly one GPU, so "device 0" means "the GPU SLURM gave me." On a personal multi-GPU box with no cgroup isolation, every concurrent job sees all GPUs and pins to device 0 — they pile onto one card (OOM / serialization) while the others sit idle. On a single-GPU machine this is a non-issue and works as-is. See §7 for the fix.

3.3 · The webapp hardcodes the SLURM profile webapp change

launch_snakemake() at webapp/pipeline_ops.py:70 and the dry-run button at webapp/run_tab.py:77 both hardcode --profile profiles/slurm/. Monitoring reads .snakemake/slurm_logs/ and uses squeue (webapp/monitoring.py:124). The webapp needs a profile-selection knob and a local (non-squeue) monitoring path.

3.4 · Data model assumes cluster shared storage data blocker

The default binds point at /n/holylfs06/LABS/kempner_shared/… — a ~700 GB ColabFold DB, ~5 GB Boltz weights, HF caches. The bind mechanism ports trivially; the 700 GB MSA database is the real obstacle for personal hardware. See §5.

5 · The data & weights problem

This is the most consequential design decision for personal use. Sizes:

AssetSizePersonal-machine strategy
ColabFold MSA DB~700 GBdon't host it Use the remote ColabFold MSA server (--use-msa-server / Boltz's MSA-server mode). Public MMseqs2 API does the alignment; you keep only inputs. This single switch removes the largest barrier.
Boltz weights~5 GBdownload once to local disk, bind-mount as today.
ESM-C / ESMFold2 HF cache~2–30 GB (size-dependent; 6B is large)existing path works scripts/download_models.py + containers/download_scripts/esm_models.sh already populate an offline cache. Recommend 600M/300M on personal GPUs; 6B needs ≥40 GB VRAM.
OpenFold weights + CCDfew GBdownload once, bind-mount.
Recommendation: ship a "local / remote-MSA" config preset where MSA runs against the public server and only Boltz/ESM weights are downloaded locally (a few GB total). That turns "need a 700 GB filesystem" into "need ~10 GB and an internet connection."

6 · Container runtime: Apptainer vs Docker

The repo is Singularity/Apptainer-only (every rule emits singularity exec --nv … -B host:ctr:ro). Personal GPU users split into two camps:

Path A — install Apptainer least code

On Linux, Apptainer is a one-line install and the existing rules work unchanged. SIFs are single files, no daemon, rootless. Recommended default for a research library — zero code change, just a docs page and prebuilt SIFs to pull.

Path B — add a Docker dispatch more reach

Most personal GPU users already have Docker + nvidia-container-toolkit. Adding a docker runtime means translating exec --nv -B a:b:ro → run --gpus all -v a:b:ro. Localized to one helper, but every rule's bind/exec string is hand-rolled today, so it touches all 6 rules unless refactored behind a container_cmd() helper first.

Platform reality check: these are CUDA images. "Personal GPU" effectively means a Linux machine with an NVIDIA card (or a cloud GPU box). macOS / Apple Silicon cannot run them at all — no CUDA. Worth stating loudly in the local quickstart so Mac users don't burn a day.

7 · GPU scheduling without SLURM

SLURM was silently doing your GPU allocation. Replacing it has a tiered answer:

Target machineApproachEffort
Single GPU Works as-is. CUDA_VISIBLE_DEVICES=0 is the one card. Just cap Snakemake to one GPU job at a time so two jobs don't share VRAM: set a gpu=1 resource on GPU rules and run with --resources gpu=1. trivial
Multi-GPU, simple Serialize GPU work to one card (waste the rest) by capping --resources gpu=1. Correct, just not fast. Good enough for an MVP. trivial
Multi-GPU, parallel Parametrize the device: replace export CUDA_VISIBLE_DEVICES=0 with a value resolved per-job. Snakemake has no native GPU-ID assignment, so use a tiny wrapper that claims a free device (lockfile / round-robin on a gpu resource of size N), then exports it before the exec --nv. Each rule changes one line. ~1–2 days

OpenFold is the exception — it already batches across GPUs via Lightning DDP using gpus_per_job, but it's wired to --gpus-per-node (SLURM). For local multi-GPU it would instead just set CUDA_VISIBLE_DEVICES to the device list and let Lightning use them.

8 · Doc/build gaps found during review

Two things the docs claim that the repo doesn't currently deliver — worth reconciling before shipping, since they'll bite a first-time external user immediately:

  • stale build.sh builds from containers/protforge-gpu.def (build.sh:44), and the README describes a "single Singularity image bundling all GPU-stage tools." That combined def does not exist — only the per-stage defs (boltz/msa/esmfold_cu/openfold) are present. So bash containers/build.sh (default mode) fails today. The real, working artifacts are the per-stage test/*_test_image.sh scripts.
  • stale README + TESTING reference containers/test/smoke.sh as the post-build check; that file is absent (only smoke.fasta and per-stage test scripts exist).
Decide the image story before the local port: either (a) build the single protforge-gpu.def the docs assume, or (b) embrace per-stage images and update build.sh/README to match. For a shippable library, (b) + publishing prebuilt images to a registry (GHCR) so users pull instead of building a ~15 GB image is the friendlier path.

9 · The work plan (phased)

Phase 0 — Single-GPU proof of life ~1 day

  1. Add profiles/local/config.yaml: drop executor: slurm, set jobs to local cores, default-resources without SLURM fields, and a gpu resource cap.
  2. Add a local config preset that sets MSA to the remote server (--use-msa-server), dodging the 700 GB DB, and points boltz.cache_dir / esmc.cache_dir at local disk.
  3. Build or pull the Boltz + ESM images on the Linux GPU box (install Apptainer).
  4. Run the ubiquitin E2E (TESTING.md §2) with --profile profiles/local/. Exit criterion: MSA→Boltz→ESM-C→ESMFold on one sequence, zero SLURM.

Phase 1 — Multi-GPU + robustness ~2–3 days

  1. Parametrize CUDA_VISIBLE_DEVICES across the 5 GPU rules (§7) + add the device-claim wrapper and a gpu resource.
  2. Reconcile the image build (§8): pick per-stage vs combined, fix build.sh, restore/author smoke.sh.
  3. Local fallback for OpenFold's --gpus-per-node path.

Phase 2 — UX & distribution (ship as a library) ~1 week

  1. Make the webapp profile-selectable (pipeline_ops.py:70, run_tab.py:77) + a local monitoring path that doesn't call squeue (monitoring.py:124).
  2. Optional docker runtime in container_cmd() for the no-Apptainer crowd (§6 Path B).
  3. Publish prebuilt images to GHCR + CI; users pull instead of build.
  4. A docs/LOCAL_QUICKSTART.md: Linux+NVIDIA requirement, driver/CUDA-12.8 check, remote-MSA preset, ~10 GB weight download, one command to run.

10 · Risks & open questions

  • Driver/CUDA floor. The ESM image needs CUDA 12.8 → a reasonably new NVIDIA driver. Old GPUs (e.g. pre-Ampere, <16 GB VRAM) will struggle with ESMFold2/Boltz at production settings. Document a minimum (suggest ≥ RTX 3090 / 24 GB; 6B model needs ≥ 40 GB).
  • Remote MSA privacy/throughput. The public MMseqs2 server is rate-limited and sends sequences off-box. Fine for academic/public work; for proprietary sequences, a personal user still needs a local DB (or a smaller UniRef subset).
  • Snakemake GPU semantics. Snakemake doesn't assign GPU IDs natively — the device-claim wrapper is custom code and the part most likely to have edge cases (crashed-job lock cleanup, etc.).
  • Boltz remote-MSA parity. Confirm Boltz's MSA-server mode produces equivalent inputs to the local ColabFold path your current configs assume (header/format differences — note the repo already ships scripts/fix_a3m_headers.py / fix_yaml_msa_paths.py, a hint this is fiddly).
  • macOS users. No CUDA path at all. The honest answer for Mac is "use a cloud Linux GPU box" — set expectations up front.
